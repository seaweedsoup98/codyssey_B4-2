# 핵심 개념: 시스템 장애를 읽는 순서

아래 개념은 **정의 → 동작 원리 → 실습 적용** 순서로 설명한다. 관련 코드는 `scripts/`에서 확인한다.

## 1단계: 실행 환경과 프로세스

### 환경변수(environment variable)

- **정의**: 프로그램 실행 시 부모 프로세스로부터 전달되는 `이름=값` 형태의 설정이다.
- **원리**: 셸의 `export MEMORY_LIMIT=256`은 이후 시작되는 자식 프로세스에 값을 전달한다. 이미 실행 중인 앱의 설정을 자동으로 바꾸지는 않는다.
- **실습**: `setup.sh`는 `AGENT_HOME`, 경로, 포트를 준비하고 `run_case.sh`는 실험마다 3가지 장애 설정만 바꾼 뒤 앱을 **새로 실행**한다. `source`는 현재 셸에 설정을 읽어 들이는 명령이다.

### 프로세스(process), PID, 프로세스 그룹(PGID)

- **정의**: 프로세스는 실행 중인 프로그램이고, PID는 그 식별 번호다. PGID는 관련 프로세스를 묶는 번호다.
- **원리**: 한 실행 파일이 부모·자식 프로세스를 모두 만들 수 있다. `ps`는 PID·PPID(부모 PID)·PGID·상태를 보여 준다. `setsid`는 별도의 세션/그룹을 시작하고 `kill -TERM -- -PGID`는 그룹에 신호를 보낸다.
- **실습**: `run_case.sh`는 대상 그룹만 관측·종료하여 다른 프로그램을 건드리지 않는다. 앱이 종료된 후에도 로그를 보존한다. `Z`는 이미 종료됐지만 부모가 아직 종료 상태를 수거하지 않은 **좀비**다.

### 스레드(thread)와 TID

- **정의**: 스레드는 한 프로세스 안에서 실행되는 작업 흐름이다. TID는 각 스레드의 식별 번호다.
- **원리**: 같은 프로세스의 스레드는 일반적으로 주소 공간을 공유하므로 공유 자원 보호를 위한 락(lock)이 필요하다.
- **실습**: `ps -eLo pid,tid,...,wchan`을 기록해 각 스레드가 실행 중인지, 커널에서 무엇을 기다리는지 확인한다.

## 2단계: 메모리 장애

### 메모리와 RSS

- **정의**: 가상 메모리는 프로세스가 사용하는 주소 공간이고, RSS(Resident Set Size)는 현재 RAM에 상주한 메모리의 크기다.
- **원리**: Heap은 프로그램이 실행 중 동적으로 할당하는 영역이다. 객체를 계속 유지하면 Heap과 RSS가 증가할 수 있다. 하지만 가상 메모리의 전체 크기(VSZ)와 RSS는 다르고, RSS에는 공유 메모리도 포함된다.
- **실습**: `monitor.sh`는 `/proc/<PID>/status`의 `VmRSS`를 KiB에서 MiB로 변환해 기록한다. 복수 PID의 RSS를 무조건 합산하면 공유 페이지를 중복 계산할 수 있다.

### 메모리 누수(memory leak), OOM, MemoryGuard

- **정의**: 메모리 누수는 더 이상 필요 없는 메모리를 회수하지 못하거나 불필요하게 유지하는 현상이다. OOM은 가용 메모리 부족 상태다.
- **원리**: 누수로 사용량이 증가하면 운영체제의 OOM Killer가 프로세스를 종료할 수도 있다. 반면 **MemoryGuard는 이 실습 앱 내부의 보호 정책**으로, 제한 초과를 감지하고 직접 프로세스를 종료하도록 설계됐다.
- **실습**: `MEMORY_LIMIT`를 올려 더 오래 생존해도 누수가 해결된 것은 아니다. 앱 로그가 자체 종료를 설명하는지, OS OOM 관련 메시지가 있는지 구분한다.

## 3단계: CPU 장애

### CPU 사용률과 처리 지연(latency)

- **정의**: CPU 사용률은 관찰 시간 중 프로세스가 CPU에서 실제 실행된 시간의 비율이다. Latency는 요청을 처리하는 데 걸린 시간이다.
- **원리**: CPU를 과도하게 사용하는 작업은 다른 프로세스·스레드가 실행될 기회를 줄여 지연을 일으킬 수 있다. 하지만 CPU 사용률이 높다는 사실만으로 요청 지연이 실제 발생했다고 단정할 수는 없다.
- **실습**: `monitor.tsv`의 구간 CPU 변화로 대상 PID의 추이를 본다. `ps %CPU`는 평생 누적 평균에 가까우므로 짧은 Spike 판단은 구간 측정이 적합하다.

### Watchdog과 종료 신호

- **정의**: Watchdog은 프로그램의 비정상 동작을 감시하고 보호 동작을 수행하는 구성 요소다.
- **원리**: 앱이 임계치 초과를 판단하면 종료를 요청할 수 있다. Linux의 SIGTERM(15)은 일반적인 종료 요청이고 SIGKILL(9)은 강제 종료다. 종료 코드 143(128+15)은 SIGTERM과 연관되지만 **신호 발신자는 식별하지 못한다**.
- **실습**: Watchdog 메시지가 있는지 확인하고, `result.txt`의 종료 이유가 `observation_limit`인지도 확인한다. 앱의 내부 `Current Load`와 OS가 측정한 CPU 값을 혼동하지 않는다.

## 4단계: 교착상태(Deadlock)

### 락(lock)과 경쟁 상태(race condition)

- **정의**: 락은 여러 스레드의 공유 자원 접근을 직렬화하는 동기화 도구다. 경쟁 상태는 실행 순서에 따라 결과가 달라지는 문제다.
- **원리**: 락이 없으면 데이터가 손상될 수 있지만, 락을 잘못된 순서로 획득하면 서로 진행하지 못할 수 있다.
- **실습**: `MULTI_THREAD_ENABLE=true`인 상태에서 로그의 락 보유와 대기 관계를 관찰한다.

### 교착상태의 4가지 필요조건

1. **상호 배제**: 자원을 동시에 둘 이상이 사용할 수 없다.
2. **점유 대기**: 한 자원을 보유하면서 다른 자원을 기다린다.
3. **비선점**: 보유한 자원을 강제로 회수하지 못한다.
4. **순환 대기**: A가 B의 자원을, B가 A의 자원을 기다리는 순환 고리가 있다.

예: `Thread-1: Lock-A 보유 → Lock-B 대기`, `Thread-2: Lock-B 보유 → Lock-A 대기`가 함께 유지되면 진행할 수 없다. 이는 **개념 예시이지 실측 로그가 아니다**.

- **실습**: PID 존재 + CPU/RSS 정체 + 로그 중단은 **무응답 징후**일 뿐이다. 실제 교착상태를 주장하려면 WAITING/BLOCKED와 자원 보유 관계 등 **순환 대기 근거**가 있어야 한다.
- **회피**: 멀티스레드를 끄는 것은 임시 우회다. 근본 대안으로 모든 스레드의 락 획득 순서 통일, 타임아웃, 임계구역 최소화 등이 있다(이 바이너리는 수정하지 않는다).

## 5단계: 증거 기반 실험

### 통제 실험과 인과관계

- **정의**: Before/After 비교는 다른 조건을 고정하고 하나의 원인 후보만 변경해 결과 차이를 확인하는 방법이다.
- **원리**: 바꾼 것이 둘 이상이면 어떤 설정이 결과를 만들었는지 분리할 수 없다. 실행 시간과 바이너리 버전도 비교 가능해야 한다.
- **실습**: `run_case.sh`의 case 분기는 각 장애별로 변수 하나만 변경한다. `settings.txt`의 바이너리 해시를 대조한다. 실행마다 별도 디렉터리를 만든다.

### 관측 사실과 해석의 구분

- **관측**: 'RSS가 20→100MiB로 증가했다'처럼 명령어 출력·시각·수치가 있는 문장.
- **해석**: '누수 가능성이 있다'처럼 여러 관측 사실에서 추론한 설명.
- **검증**: 설정을 변경하고 반복해 같은 결과를 얻었는지 확인하는 과정.

관측값을 만들지 말고, 재현이 실패했으면 '재현 실패'라고 기록한다. **다른 사람의 리포트 숫자는 내 실험의 실측 증거가 아니다.**
